# 설문 기반 난임 위험 예측 서비스

사용자의 설문을 모델 입력으로 바꾸고, 예측 점수와 설명 보고서를 제공하는 팀 프로젝트입니다. 저는 데이터 전처리와 파생변수 구성, XGBoost·LightGBM 학습과 Optuna 탐색, FastAPI 추론 API, Spring Boot 연동과 결과 저장, AWS EC2 배포를 맡았습니다. 데이터를 학습 가능한 형태로 만드는 작업부터 웹서비스에서 결과를 조회하고 배포 문제를 확인하는 과정까지 담당했습니다.

## 데이터를 합치고 학습 방식을 바꾼 과정

NSFG 설문을 성별 특성에 맞게 전처리하고 모델을 학습했습니다. [여성 모델 학습 기록](training/README.md)에는 다섯 조사 주기의 DAT/DCT·CSV를 읽어 합치고, 주기마다 다른 변수명을 통일한 코드가 남아 있습니다. 결측을 뜻하는 응답 코드를 정리하고 BMI의 단위를 맞췄으며, 출산력·연령·질환 등의 값으로 파생변수를 구성했습니다. 단순히 알고리즘을 바꾸는 것보다 먼저, 같은 뜻의 응답이 같은 변수로 들어오는지 확인해야 했습니다.

양성 사례가 적어 초기에는 SMOTE로 표본을 늘리는 방법도 시험했습니다. 실험 결과를 검토한 뒤 합성 표본을 늘리는 방식에서 원본 표본에 가중치를 주는 방식으로 전환했습니다. 보관한 여성 학습 코드에서는 클래스 빈도, 조사 시점, 정규화한 설문 표본 가중치를 곱해 `sample_weight`를 만들고 모델 학습에 전달합니다. 이 자료만으로 SMOTE 제거에 따른 정확한 개선 폭을 재현할 수는 없어, 성능 상승률 대신 제가 비교하고 변경한 과정을 제시합니다.

XGBoost와 LightGBM을 각각 학습하고 Optuna로 하이퍼파라미터를 탐색했습니다. 여성 코드에는 계층화 80:20 분할, 3-fold 교차검증, 모델별 100회 탐색 설정과 0.6/0.4 Soft Voting 구성이 있습니다. 당시 실험 코드를 [학습 코드 사본](training/female_training_original.py)으로 넣었습니다. 이 세부 설정은 보관한 여성 모델 실험 기준이며, 현재 배포 모델의 확정 설정과는 구분합니다. 평가 방식에서 남은 과제도 학습 기록에 함께 적었습니다.

## 학습한 모델을 서비스 입력과 연결

서비스에서는 키·몸무게·흡연량 같은 설문값을 받지만, 모델은 학습 때 정한 컬럼과 파생변수를 기대합니다. 저는 범주형 응답을 변환하고 성별에 맞게 요청을 구성했습니다. FastAPI에서는 입력 키의 별칭과 결측값을 정리하고, 성별 피처를 구성한 뒤 `feature_names_in_` 순서로 열을 맞췄습니다. 남성 입력의 자녀 수·성생활 관련 값과 여성 입력의 출산력·초경·질환 관련 값을 구분하는 로직도 이 과정에 들어 있습니다.

Spring Boot에서는 검사 세션을 기준으로 설문을 누적하고, 인증된 사용자가 자신의 세션과 결과를 다루도록 조회 범위를 제한했습니다. 현재 제출 코드에서 세션 소유 확인과 기존 결과 확인, 성별 요청 변환, AI 응답의 상태·본문·점수 검사와 PostgreSQL 저장 흐름을 볼 수 있습니다.

AI 서버와 연결되는 부분에는 연결·읽기 타임아웃과 기능 플래그를 넣었습니다. 현재 코드의 기본 타임아웃은 연결 2초, 읽기 5초이며 설정으로 바꿀 수 있습니다. AI를 준비하지 않은 개발 환경에서는 플래그를 끄고 더미 결과로 제출 흐름을 확인할 수 있습니다. 이는 개발용 분기이고, 운영 중 AI 호출이 실패하면 자동으로 정상 예측을 돌려주는 기능은 아닙니다.

## 핵심 결과 저장과 LLM 설명 요청을 분리

핵심 예측과 외부 LLM의 설명 생성도 나눴습니다. 점수와 위험 요인 목록은 먼저 저장·반환하고, 상세 설명은 별도 조회 요청에서 생성하도록 구현했습니다. LLM은 예측 점수를 결정하는 모델이 아니라 결과를 설명하는 용도로 사용했습니다. 설명 생성의 성공 여부와 관계없이 핵심 결과를 저장하고 조회할 수 있는지 확인했습니다.

현재 제출 코드는 이후 팀의 수정이 반영된 통합본입니다. 설명 보고서 재사용과 미션 연계 등 후속 확장도 함께 들어 있으며, 아래 링크에서는 제가 맡은 초기 연동 구조와 현재 구현을 볼 수 있습니다.

## 로컬과 배포 서버의 응답이 달랐던 이유

로컬에서는 입력에 따라 위험 요인의 개수가 달라졌지만, EC2에서는 항상 세 개만 반환되는 문제가 있었습니다. 저는 Spring의 응답과 AI 서버의 원본 응답을 비교하고, 서버의 실행 프로세스와 가상환경을 차례로 확인했습니다. 그 결과 수정 전 코드로 실행 중인 Uvicorn 프로세스를 찾아 올바른 환경으로 다시 실행했습니다. 이후 입력에 따라 위험 요인의 개수가 달라지는지 확인했습니다.

이 일을 겪고 실행 중인 코드의 버전을 확인할 수 있도록 시작 시 커밋 정보를 기록했습니다. 소스를 수정했다는 사실만으로 배포가 반영됐다고 판단하지 않고, 실제 프로세스와 응답까지 확인하는 습관을 갖게 됐습니다.

현재 [운영 가이드](ai/OPERATIONS_TOP_FACTORS.md)와 [API 계약 테스트](ai/tests/test_predict_top_factors.py)에는 위험 요인 배열을 확인하는 방법이 남아 있습니다. 테스트는 mock 응답으로 0·1·2·3·7개 배열을 점검하며, 실제 모델의 예측 정확도를 평가하는 테스트와는 구분됩니다.

## 팀 작업 범위

이 제출본의 백엔드와 AI 서버는 팀의 후속 수정이 반영된 통합 코드입니다. 제 담당은 설문 전처리·파생변수와 모델 학습, 추론 API, 검사 세션과 사용자별 결과 처리, Spring Boot·DB 연동, LLM 설명 요청 분리, AWS 배포와 응답 문제 진단입니다. 인증, 홈 화면, 중간 저장의 후속 확장, 미션, 커뮤니티와 후속 리포트 개선에는 다른 팀원의 작업이 포함되어 있습니다. 프론트엔드 전체나 현재 통합본의 모든 기능을 제가 구현한 것은 아닙니다.

## 현재 한계와 제출본 실행 범위

- 위험 요인 목록은 입력에서 활성화된 플래그를 규칙에 따라 추출합니다. SHAP 설명이나 의학적 인과관계 분석이 아닙니다. 예측 점수 역시 임상적으로 검증된 진단 결과나 개인의 난임 확률이 아닙니다.
- AI 호출부는 `WebClient`의 `.block()`으로 결과를 기다리는 동기 처리입니다. 핵심 결과와 설명 요청을 나눈 것과 전체 서비스를 비동기로 구현한 것은 별개입니다.
- `training/`에는 여성 모델의 학습 실험 코드만 포함했습니다. 학습 데이터, 남성 학습 코드, 남녀 모델 바이너리와 원시 실험 로그, 실제 사용자 설문·의료 기록은 포함하지 않았습니다. 모델 파일이 없어 이 사본만으로 실제 추론을 실행할 수 없고, 데이터·환경이 없어 당시 학습 성능을 재현한 것도 아닙니다.
- 백엔드 실행에는 DB·인증·AI·LLM 설정이 별도로 필요합니다. 이번 제출본 정리에서는 전체 빌드·통합 테스트와 외부 API 실행을 수행하지 않았습니다. 당시 운영 로그와 화면 기록도 포함하지 않았습니다.
- Git 이력, 운영 주소·설정·배포 workflow, 빌드 산출물, 운영용 smoke 스크립트와 개인·팀 식별 문서는 제외했습니다. 테스트 이메일은 예약된 예시 도메인으로 바꿨습니다.

기존 제3자 빌드 도구의 저작권·라이선스 고지는 유지했으며, 팀 프로젝트 전체에 새로운 오픈소스 라이선스를 부여하지 않았습니다.
