# ICT 개발 포트폴리오

Java와 Spring Boot로 사용자 입력을 저장·조회하고, 외부 금융 API와 AI 서버를 연결하는 백엔드를 개발했습니다. 서비스가 정상적으로 응답하는 것에서 그치지 않고, 여러 건의 데이터 중 무엇을 조회할지, 인증 정보가 잘못됐을 때 어떻게 처리할지, 배포 후 응답이 달라진 이유가 무엇인지 확인해 왔습니다.

아래 여섯 프로젝트에 담당 기능과 코드를 정리했습니다. 백엔드 개발 경험은 **GIVY → Referoom → 난임 예측 서비스** 순서로 보시면 됩니다.

## 대표적인 문제 해결 경험

### 여러 계좌 이력 중 어떤 데이터를 보여줄 것인가

GIVY에서 한 사용자에게 계좌 연동 이력이 여러 건 남아 있으면 단건 조회가 실패했습니다. 이력을 지우기보다 홈에 어떤 정보를 보여줄지 PM과 먼저 정했고, 최근 이력 한 건을 선택하도록 조회를 수정했습니다. Swagger로 홈 응답을 확인했습니다. 당시 수정과 이후 팀이 변경한 최종 조회 조건은 [프로젝트 설명](givy/README.md)에 구분해 두었습니다.

### 서로 다른 서비스에서 인증 기준을 맞추기

레퍼룸의 Spring Boot 인증 서버와 Python 서비스가 같은 JWT와 팀 권한을 확인하도록 공통 처리를 맡았습니다. 인증 서버에서는 잘못된 Bearer 토큰이 있어도 정상 쿠키로 우회해 통과하지 않도록 했습니다. Python 공통 패키지에는 인증·권한 검사와 오류 응답, 요청 로그를 묶고 테스트를 작성했습니다.

- [Java JWT 필터](referoom/auth-server/app/src/main/java/workplace/security/JwtAuthenticationFilter.java)
- [Python 인증·권한 처리](referoom/common-py/referoom_common/auth.py) · [테스트](referoom/common-py/tests/)

### 로컬과 배포 환경의 응답이 달랐던 이유 찾기

난임 예측 서비스에서 입력을 바꿔도 배포 서버의 위험 요인이 항상 세 개로 반환됐습니다. Spring 응답, 로컬 AI 서버, EC2 실행 프로세스를 차례로 비교해 이전 버전의 Uvicorn 프로세스가 남아 있음을 확인했습니다. 올바른 환경에서 다시 실행하고 입력에 따라 응답이 달라지는지 확인했습니다. 이후 실행 커밋을 기록해 배포 버전을 확인할 수 있게 했습니다. [처리 흐름과 운영 가이드](fertility/README.md)에 관련 코드를 연결했습니다.

## 기여 범위와 자료 안내

ESS는 공개 실험 데이터를 사용한 개인 프로젝트이고, 나머지 다섯 개는 팀 프로젝트입니다. 각 README에서 제가 담당한 기능과 팀의 공통 구현·후속 변경을 구분했습니다. 팀 코드와 제3자 자료의 권리는 원저작자에게 있습니다.

이 저장소는 기존 프로젝트의 특정 시점 코드를 모은 제출용 사본입니다. 과거 Git 이력, 개인 식별정보가 포함된 보고서, 실제 인증 설정과 배포 주소, 모델 바이너리는 제외했습니다. 원본 데이터나 외부 API가 필요한 프로젝트는 별도 환경 설정이 필요합니다.

확인한 테스트와 저장된 실험 결과, 아직 검증하지 못한 부분은 프로젝트별 README에 적었습니다. 실제 금융 시스템 운영 실적이나 의료적 진단 성능을 평가한 자료는 아닙니다. 외부 논문과 데이터셋의 연구기관·저자 표기는 자료 출처입니다.
