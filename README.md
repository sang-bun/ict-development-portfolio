# ICT 개발 포트폴리오

Java와 Spring Boot로 인증·조회·저장 API를 만들고, 외부 금융 API와 Python 기반 AI 서버를 연결했습니다. 모델을 학습하는 과정부터 사용자가 결과를 조회하는 과정까지 직접 다뤄 보면서, 데이터의 의미와 실행 중인 서비스의 동작을 함께 확인해 왔습니다.

아래 여섯 프로젝트에 제가 맡은 기능, 구현 중 내린 판단, 확인한 결과를 정리했습니다. 상세 문서에서 관련 코드와 실험 자료를 볼 수 있습니다.

## 프로젝트별 구현과 판단

### GIVY — 화면에서 필요한 데이터의 기준 정하기

인증과 투자 성향 분류를 구현하고, 챌린지 참여 전후에 따라 홈의 응답을 다르게 구성했습니다. 팀의 KIS 클라이언트에서 받은 현재가·52주 범위·일별 종가를 화면에 필요한 형태로 조합했습니다.

한 사용자에게 계좌 연동 이력이 여러 건 남으면 단건 조회가 실패했습니다. 이력을 지우기보다 홈에 어떤 정보를 보여줄지 PM과 정했고, 최근 이력 한 건을 선택하도록 수정한 뒤 Swagger로 응답을 확인했습니다. 당시 수정과 팀의 후속 조회 조건, 외부 시세 실패 시 기본값 처리의 한계도 함께 기록했습니다.

[담당 기능과 홈 API](givy/README.md) · [홈 조회 코드](givy/src/main/java/com/example/givy/domain/home/service/query/HomeQueryServiceImpl.java)

### Fitty — 개별 API를 시연 가능한 흐름으로 연결하기

운동 기록 생성·삭제를 주간 목표의 횟수·거리·시간 갱신과 연결했습니다. 캐릭터 생성·조회·수정과 운동 기록의 댓글 작성·최신순 페이지 조회도 맡았습니다. 목표 진행도의 증감·음수 방지 규칙은 팀의 도메인 코드를 사용했습니다.

프론트엔드와 요청 형식·구현 범위가 달라 재작업이 생겼을 때, 완료한 기능과 남은 API를 정리하고 실제 요청·응답 예시를 맞췄습니다. 운동 기록에서 캐릭터 피드백까지 먼저 연결하고 알림은 시연에서 제외하자고 제안해 팀과 합의했고, 기한 안에 핵심 흐름을 시연했습니다.

[기능별 구현과 협업 과정](fitty/README.md) · [운동 기록 서비스](fitty/src/main/java/umc/fitty/service/RunRecordService/RecordCommandServiceImpl.java)

### 난임 예측 서비스 — 모델 학습에서 결과 조회까지

설문 데이터의 전처리와 성별 피처 구성, XGBoost·LightGBM 학습과 Optuna 탐색을 맡았습니다. 불균형 데이터 처리에서는 SMOTE를 비교한 뒤 합성 표본을 늘리지 않는 가중치 학습으로 변경했습니다. 별도로 남겨 둔 여성 모델 학습 코드에는 조사 주기별 데이터 통합, 클래스·조사 시점·표본 가중치 계산과 앙상블 구성이 담겨 있습니다.

학습 결과를 FastAPI와 Spring Boot로 연결하고, 핵심 예측은 먼저 저장·반환하되 LLM 설명은 별도 조회로 분리했습니다. EC2에서 입력과 관계없이 위험 요인이 세 개만 반환되는 문제는 이전 Uvicorn 프로세스를 찾아 해결했습니다. 모델 평가의 한계와 서비스 동작 확인은 구분해 적었습니다.

[학습·연동·배포 과정](fertility/README.md) · [학습 자료](fertility/training/README.md) · [추론 입력 구성](fertility/ai/fertility_inference_engine.py)

### Referoom — 서로 다른 서비스의 인증·권한 기준 맞추기

Spring Boot 회원·팀 인증 서버와 Python 서비스용 공통 패키지를 맡았습니다. 잘못된 Bearer 토큰이 정상 쿠키로 우회되지 않도록 처리하고, 관리자 요청은 토큰의 역할뿐 아니라 DB의 팀 소속·권한도 확인했습니다. 공통 패키지에는 인증·권한, 오류 응답, 요청 로그와 테스트를 묶었습니다.

DB 초기화와 초기 E2E 점검을 준비하고, 요청 로그에서 지연·오류·토큰·비용을 집계하는 스크립트도 작성했습니다. 민감한 로그는 집계에서 제외하도록 했습니다. 제출 사본의 공통 모듈 테스트 131개 통과는 제 초기 작업과 팀의 후속 변경을 포함한 통합본 결과입니다.

[인증 사례와 운영 리포트](referoom/README.md) · [공통 모듈 테스트](referoom/common-py/tests/) · [운영 집계 코드](referoom/scripts/ops_report.py)

### VentureSignal — 근거가 부족한 결과를 점수로 확정하지 않기

시장성 평가와 투자 판단 에이전트의 초기 구현을 맡았습니다. 시장 규모를 연도·단위·출처와 함께 정리하고, 생성된 본문 인용과 근거 목록이 입력 자료에 있는지 대조했습니다. 점수가 있어도 근거가 없거나, 미산정 항목에 추가로 필요한 정보가 없으면 검증에서 거절하도록 했습니다.

출력 스키마와 점수 범위를 검증하고 가중합 계산을 연결했습니다. 투자조건을 제외한 필수 항목의 점수가 없으면 총점 산정을 보류했습니다. 이후 팀이 개선한 출처 번호화·점수 재정규화·추가 채점은 제 초기 구현과 구분해 소개합니다.

[개인 구현과 검증 사례](venturesignal/README.md) · [투자 판단 코드](venturesignal/agents/investment_decision/node.py)

### ESS 배터리 수명 예측 — 평균 오차 뒤의 실패 사례까지 확인하기

공개 배터리 실험 데이터를 개인적으로 분석했습니다. MATLAB 객체 참조와 수명 라벨을 점검하고, 초기 100사이클 이내 피처를 추출했습니다. 충전 프로토콜을 기준으로 검증 데이터를 나누고 9개 후보를 비교해, ΔQ 로그 분산 하나를 사용하는 로그 선형 모델을 선택했습니다.

내부 hold-out MAPE는 9.146%였지만 다른 배치에서는 26.175%로 커졌습니다. 셀별 결과를 살펴 39개 중 38개를 과대 예측한 사실을 기록했고, 작은 평균 오차만으로 실제 교체 판단에 사용할 수 없다고 해석했습니다. 저장된 예측 CSV와 결과 그래프를 함께 제공합니다.

[분석·모델 선택·결과 그래프](ess-battery/README.md) · [성능표](ess-battery/results/model_performance.csv)
